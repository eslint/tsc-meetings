### [fix: include --no-inline-config and --quiet in cache validity](https://github.com/eslint/eslint/issues/21448)

**TSC Summary:** The PR fixes stale cached lint results when `--no-inline-config` or `--quiet` changes between runs. It adds `allowInlineConfig` and the built-in `--quiet` rule-filter status to cache validity, while preserving compatibility between `--quiet --max-warnings` and ordinary cached results. The author reverted a proposed change that disabled cache reuse with a custom API `ruleFilter` after concerns that this could be breaking in a semver-minor release.

* @mdjermanovic noted that the question about semver compatibility no longer applies to the current PR, though the TSC could discuss whether changing custom `ruleFilter` cache behavior should be considered breaking.
* @fasttime agreed that the earlier question no longer applies and suggested discussing any desired change to current behavior in a follow-up on the issue.

**Resolution:** The TSC had no decision to make on the current PR. The behavior of caching with a custom `ruleFilter` can be discussed in a follow-up.

### [Change Request: Remove `ExperimentalRestProperty` and `ExperimentalSpreadProperty` from visitor keys](https://github.com/eslint/js/issues/779)

* @mdjermanovic said removing the node types might be safest to bundle with the next major version, but @nzakas questioned the need to remove them at all given the compatibility risk to parsers and the lack of a substantive benefit.
* @fasttime suggested documenting the node types as deprecated. The TSC felt that this would not be worth the effort.

**Resolution:** The TSC agreed not to move forward with this change and to close the issue.

### [feat: replace eslint-plugin-react with @eslint-react](https://github.com/eslint/create-config/pull/273)

* @mdjermanovic asked whether the proposed `typescript@~6.0.3` dependency should be included unconditionally alongside `@typescript-eslint` or `@eslint-react/eslint-plugin`, since TypeScript is a peer dependency of those packages. He was concerned that hardcoding the range could override a user's choice.
* @nzakas agreed that the version should not be hardcoded. @fasttime noted that package managers generally install peer dependencies automatically and suggested warning about an incompatible version or Yarn 1; the TSC agreed there was no need to install TypeScript in the generated configuration.
* The related [issue](https://github.com/eslint/create-config/issues/273) had previously been resolved as a semver-minor `feat`. The question discussed here was raised in [the PR discussion](https://github.com/eslint/create-config/pull/273#discussion_r4436599983).

**Resolution:** The TSC agreed not to hardcode `typescript` as a dependency.

### Appointing Project Leads for ESLint Subprojects

* @nzakas proposed appointing project leads for some ESLint subprojects to help ensure packages are maintained and issues, PRs, and releases do not fall through the cracks. The leads would be existing team members and could make day-to-day decisions about accepting issues, merging PRs, and publishing releases.
* @fasttime suggested establishing minimum shared requirements, such as supported Node.js versions. The TSC would continue to set global standards while project leads handle day-to-day operations.

**Resolution:** The TSC agreed to start appointing project leads for subprojects.

**Action Items:**

  - Determine how to proceed if multiple people volunteer to lead the same project.

### Retiring the Contributor Pool

* @nzakas proposed retiring the contributor pool because evaluating whether contributions were AI-generated has become difficult and time-consuming, undermining the program's original goal of encouraging and rewarding contributions.
* @mdjermanovic and @fasttime agreed. The TSC noted that awards were always discretionary and not a job or guarantee.

**Resolution:** The TSC agreed to retire the contributor pool.

**Action Items:**
