### [Change Request: record when the fix loop exits at MAX_AUTOFIX_PASSES — the part of #19321 that the circular-fix detection from #17609 does not cover](https://github.com/eslint/eslint/issues/21223)

* The issue proposes reporting when autofix reaches its 10-pass limit while fixable problems remain. It notes that this is distinct from the circular-fix warning added in [eslint/eslint#17609](https://github.com/eslint/eslint/issues/17609); [eslint/eslint#21288](https://github.com/eslint/eslint/pull/21288) was closed pending acceptance of the issue.
* @mdjermanovic noted that a formatter can already see remaining fixable messages; a warning would be visible regardless of the formatter and could be emitted once per file with the filename.
* @mdjermanovic and @fasttime did not feel strongly about adding a warning, and @nzakas noted the case is rare but a warning could be useful.

**Resolution:** The TSC agreed not to accept the proposal and to leave the behavior as-is.

### [Bug: `ConfigCommentParser` returns regex literals with modern flags such as `u`, `s`, `d`, `v` as strings](https://github.com/eslint/rewrite/issues/527)

* @nzakas clarified that the issue concerns modern regular expression flags; older flags (`gimy`) are recognized and returned as regular expression objects.
* @mdjermanovic noted that regex values in rule options are not supported intentionally, and that rule options and settings should be JSON-like data. The TSC agreed that regex literal support is accidental and can cause problems, including with caching.
* The TSC agreed to make no changes now and to research a possible v11 breaking change to remove support for regex option values, including checking for existing usage. [eslint/eslint#13447](https://github.com/eslint/eslint/issues/13447) was mentioned as a previous breakage related to this behavior.

**Resolution:** Close [eslint/rewrite#527](https://github.com/eslint/rewrite/issues/527). The TSC will discuss potentially removing regex option values for v11 in a separate issue.

**Action Items:**
- @mdjermanovic will:
  - Open an issue to discuss potentially removing support for regex option values in v11 and research the impact.

### [Bug: `--cache` ignores changes to regular expressions in rule options and settings](https://github.com/eslint/eslint/issues/21438)

* The issue describes stale cached results after a regular expression in a rule's options changes. @fasttime noted the same problem can occur with any non-serializable value that disappears during serialization.
* The TSC agreed that non-serializable rule-config values cannot be cached and can cause unpredictable behavior; their working accidentally is a bug, not a feature. The TSC discussed updating documentation to discourage their use in v10 and considering whether a future issue should cover all non-serializable rule options, not only regexes.

**Resolution:** Update the documentation to discourage using non-serializable values in rule configs.

**Action Items:**
- @mdjermanovic will:
  - Update the documentation to discourage the use of non-serializable values in rule configs.
