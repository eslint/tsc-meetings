### [Change Request: record when the fix loop exits at MAX_AUTOFIX_PASSES — the part of #19321 that the circular-fix detection from #17609 does not cover](https://github.com/eslint/eslint/issues/21223)

**TSC Summary:** Autofix stops after 10 passes. If pass 10 still changes the file and fixable problems remain, ESLint currently stays silent. Circular fixes already produce a warning, but that warning covers a different situation ([#17609](https://github.com/eslint/eslint/issues/17609)). The proposal is to report when the pass limit is reached; [#21288](https://github.com/eslint/eslint/pull/21288) was closed until this issue is accepted.

* @mdjermanovic said formatters already have access to the remaining fixable messages; a formatter message could refer to updating the default stylish formatter.
* @nzakas thought a warning would be consistent with the circular-fixes warning and visible regardless of the formatter.
* @fasttime asked whether there would be one warning per file; @nzakas confirmed that there would be, with the filename in the message.
* The TSC was not strongly in favor of adding a warning and agreed to leave the behavior as-is.

**Resolution:** The TSC agreed to reject the proposal and leave the behavior unchanged.

### [Bug: `ConfigCommentParser` returns regex literals with modern flags such as `u`, `s`, `d`, `v` as strings](https://github.com/eslint/rewrite/issues/527)

**TSC Summary:** `levn`, used for config comment parsing, recognizes regular expressions with older flags (`gimy`) but returns regex literals with modern flags as strings. The TSC discussed whether to fix this or fork `levn`.

* @mdjermanovic said the team has not supported regex values in rule options and settings, which are intended to be JSON-like data; regex values also cause caching problems.
* @nzakas agreed that regex literals falling through are a bug rather than a feature, and proposed considering a breaking change to remove regex support entirely. The TSC recalled a prior breakage ([Config json cloning is a BREAKING CHANGE!](https://github.com/eslint/eslint/issues/13447)), so further research is needed.

**Resolution:** The TSC agreed not to make changes now, to open a v11 tracking issue to discuss potentially removing support for regex option values, and to close this issue.

**Action Items:**
- @mdjermanovic will:
  - Open an issue to discuss potentially removing support for regex option values in v11.

### [Bug: `--cache` ignores changes to regular expressions in rule options and settings](https://github.com/eslint/eslint/issues/21438)

**TSC Summary:** Changing a regular expression in a rule's options while using `--cache` can leave the cache valid and reuse stale results. The issue may also apply to other non-serializable values that disappear during serialization.

* @mdjermanovic said this issue would be avoided if regex values were no longer supported.
* @fasttime noted that non-serializable values beyond regexes, such as callbacks or bigints, may cause the same problem.
* The TSC agreed that non-serializable values cannot be cached and can cause unpredictable behavior; their current behavior is a bug, not a feature. The documentation should discourage their use in rule configs while still in v10, and the proposed v11 issue can consider whether to address all non-serializable values.

**Resolution:** The TSC agreed to update the documentation to discourage using non-serializable values in rule configs.

**Action Items:**
- @mdjermanovic will:
  - Update the documentation to discourage using non-serializable values in rule configs.
